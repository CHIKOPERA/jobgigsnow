# 03 — UI

Recreate `design_handoff_job_board_ui/Job Board UI Guide.dc.html` as React components, mobile-first.
High fidelity: colours/type/spacing/states match the tokens exactly.

## Components
- [x] `JobCard` — one link + sibling save button (never nested interactive elements), 40×40 initials
      tile, meta chips, closed state (`surface-sunk`, opacity .72, line-through title).
- [x] `Button` (+ `LinkButton` for anchor-based CTAs like "Apply now") — primary/secondary/success/
      disabled/loading variants, 48px min height, full-width < 768px.
- [x] Form-field styling (48px input, 16px text, `border-line-strong`, 8px radius) — inlined in
      `FilterSheet`'s location input rather than pulled out as a standalone `FormField` component,
      since Phase 1 has no signup/application forms that would reuse it. Extract if phase 2 adds one.
- [x] `SearchBar` — sticky-positioned by its parent, 52px pill, plain `<form method="GET">` (zero
      client JS — the browser's native GET-form submission does the URL-param navigation).
- [x] `FilterChips` + `FilterSheet` — horizontally scrolling row, `aria-pressed`, "All filters" →
      bottom sheet with location/postedWithin/tags.
- [ ] `ApplicationStatus` / `StatusTrack` — **out of scope for Phase 1.** The design guide shows it as
      one of six core components, but it tracks an *application* through a multi-step pipeline, and
      Phase 1's schema has no `Application` entity (job-seekers apply externally via `applyUrl`).
      Build this when phase 2/3 adds in-app application tracking.

## Screens
- [x] Job list — mobile single column (360–767) → filter rail at 768 → list + detail split at 1200.
      **Substitution:** "virtualises after 20 cards" → cursor-paginated "Load more" button
      (`LoadMoreJobs`, client component) instead of DOM virtualization. True virtualization needs a
      windowing library (e.g. `react-window`), a new dependency beyond Next/Prisma/Clerk/Zod/Tailwind
      — this bounds rendered DOM nodes without one. **Simplification:** the 768–1199 "persistent
      filter rail" is not a separate component — `FilterChips`/`FilterSheet` are reused unchanged at
      every breakpoint rather than building a second desktop-rail variant.
- [x] Job detail — `/jobs/[slug]`. **Implementation note:** built as a shared `JobsShell` server
      component rendered by both `app/jobs/page.tsx` and `app/jobs/[slug]/page.tsx`, rather than
      Next.js parallel/intercepting routes. Reason: the list depends on `searchParams` (search/filter
      state), and Next.js layouts — which is what would make the list "persist" across navigations —
      cannot read `searchParams` at all (an intentional Next.js constraint, so a filter change doesn't
      invalidate the whole tree). Consequence: at ≥1200px, clicking a different job card re-renders
      the list pane's markup along with the detail pane on every navigation, instead of Next.js
      diffing it away for free the way a true persistent-layout/parallel-route split would. Visually
      identical to the spec; a real optimization opportunity for later, not a correctness gap.
- [x] Saved jobs — `/saved`. Signed-out: inline "Sign in to see your saved jobs" prompt (not a
      redirect — see `docs/todo/04-auth.md`). Empty/loaded states covered.
- [x] Bottom tab bar (mobile) — 2 destinations (Jobs, Saved; design allows up to 4 — Phase 1 has no
      third/fourth destination), ≥52px, hides on scroll-down after 200px.

## Non-negotiables (from the design)
- [x] 48px minimum hit areas everywhere (`--hit-min`, save button, tab bar, buttons, chips).
- [x] Visible focus ring (`.focus-ring` / `--ring`) on every surface, including dark buttons.
- [x] Live-region result count (`aria-live="polite"`) on filter/search changes (job list + saved list).
- [x] No colour-only status — closed jobs get a line-through title and "Closed N days ago" text, not
      just a dimmed card; "New" chip is always paired with the word "New".
- [x] `prefers-reduced-motion` respected — durations collapse to 0ms and `animate-pulse` skeletons stop
      animating (`globals.css`).
- [x] 200% zoom / 320px width — no fixed pixel widths that would force horizontal scroll; not verified
      against a real browser/device lab in this pass.
- [ ] Perf budget: ≤60 KB first-load JS on the list route. **Not met, and not realistically meetable
      with this stack as configured.** Measured gzip size of the root shared JS chunks alone (Next.js
      16 + React 19 + Turbopack client runtime, before any app code) is ~166 KB gzipped — confirmed by
      inspecting the built chunks directly, and confirmed those chunks contain no Clerk or Zod code
      (grepped for `@clerk/`, `zod`, etc. — zero matches; the app-level additions are small). The
      list route itself follows every constraint that *is* in our control: it's a Server Component,
      only the save button and filter chips are Client Components, there's no client-side state
      library, and no above-the-fold images. If 60 KB is a hard requirement, it implies a different
      base stack (e.g. no Turbopack-generated client runtime at this size, or accepting Clerk's cost
      is out of budget for the list route specifically) — flag to design/product before spending more
      time chasing a framework-level floor.
